# HMS restructure — decision log

One line per decision: date, decision, reason. Append-only; do not edit past entries.

- 2026-07-18 — Root `/` temporarily redirects to `admin.login` instead of a marketing page. Reason: the True-Doctor scan-first home retired with the registry domain (Phase 0 Step 1); the real SaaS marketing/landing page is Phase 0 Step 5 scope (HMS_PLAN.md §7.5). Placeholder keeps the app bootable in between.
- 2026-07-18 — `RbacSeeder`/`AdminUserSeeder` trimmed to a single `super_admin` role/account for Phase 0 Step 1, instead of carrying the retired registry roles (registrar/verifier/auditor/institution_admin/data_clerk) forward. Reason: those roles only gated retired registry features; Phase 0 Step 5 seeds the real HMS RBAC matrix (Hospital Admin, Doctor, Nurse, Receptionist, Pharmacist, Lab Technician, Radiologist, Accountant — HMS_PLAN.md §5). Carrying them forward would have left dead permission strings.
- 2026-07-18 — District seeding extracted from the retired `RegistrySeeder` into a standalone `DistrictSeeder`. Reason: `districts` is a kept asset (HMS_PLAN.md §1) independent of the registry domain; patient address fields (§4) will depend on it from Phase 1.
- 2026-07-18 — The seeded Super Admin password (`4321`) was left in place during Phase 0 Step 1. Reason: removing default passwords is explicitly Phase 0 Step 4 scope (constraint C14); changing it mid-Step-1 would be out-of-order scope creep. Tracked as a known interim gap in `AdminUserSeeder`'s docblock.
- 2026-07-18 — `Subscription` (central/SaaS-layer per HMS_PLAN.md §2 diagram) was still given the `BelongsToHospital` trait in Phase 0 Step 3, alongside `hospitals`/`plans`/`subscriptions` migrations. Reason: it has a real `hospital_id` and conceptually belongs to exactly one hospital; scoping it is a no-op for super-admin's default unscoped view and correct defense-in-depth for any future hospital-facing billing screen — the alternative (leaving it unscoped and relying on call sites to filter manually) is exactly the "manual per-query filtering" constraint B8 forbids. `Hospital` and `Plan` do not get the trait — they aren't owned by a single hospital.
- 2026-07-18 — `HospitalScope` treats "no current hospital resolved" as **unscoped** (no filter), never as "filter to nothing". Reason: the alternative would silently empty every query in console/queue/seeder contexts (no HTTP request → no resolved tenant) and for a super-admin who hasn't switched into a hospital — its own class of tenancy bug. The isolation guarantee comes from a *resolved* context always filtering correctly, not from an unresolved one pretending to be empty.
- 2026-07-18 — Discovered Laravel's slimmed-down skeleton leaves the `api` middleware group unthrottled unless `$middleware->throttleApi()` is explicitly called (`apiLimiter` defaults to `null` in `Illuminate\Foundation\Configuration\Middleware`). Fixed in Phase 0 Step 4 alongside the other C-series hardening rather than treated as a separate task — it's the same "rate limiting... 0-byte/unregistered" failure class the plan calls out, just a framework-default version of it instead of a stub file.
- 2026-07-18 — Password policy set to min 8 + letters + numbers (not a longer/symbol-required policy). Reason: this is internal hospital-staff tooling behind an invite/admin-created-account model (no public self-registration), not a consumer product; balances constraint C14's "password policy enforced" against not over-engineering a rule for a threat model that doesn't call for it. Revisit if Phase 5's security audit (§22) says otherwise.
- 2026-07-18 — `RbacSeeder` seeds only `access-admin`/`manage-users`/`manage-settings`/`manage-hospitals`/`manage-plans`/`manage-subscriptions` for the 10 HMS roles (Phase 0 Step 5), not the full `module.action` permission set (`patients.create`, `billing.refund`, `pharmacy.dispense`, …) HMS_PLAN.md §5 describes. Reason: those permissions gate modules that don't exist until Phase 1+; seeding them now, with no route or Policy anywhere checking them, is exactly the "permission nothing enforces" flavor of the scaffolding constraint A4 bans. Each module seeds and assigns its own permissions when it ships.
- 2026-07-18 — Fixed `UserController`'s role validation whitelist (`admin,instructor,moderator,student,officer,frontdesk` — stale leftover from an even earlier, pre-True-Doctor product, matching none of the roles the create/edit forms actually offered) as part of Phase 0 Step 5's RBAC seed. Reason: this wasn't a design call, it was already broken — every staff-creation submission through the visible dropdown would have failed validation. Fixed alongside the HMS role rollout since I was already touching every role reference in the app.
- 2026-07-18 — Giving `hospital_admin` the `manage-users` permission (Phase 0 Step 5's RBAC matrix) would have let one hospital's admin see/edit another hospital's staff through `/admin/users`, since `User` doesn't (and can't) carry the `BelongsToHospital` global scope — super-admin accounts (`hospital_id` null) must coexist with hospital-scoped ones in the same table. Added explicit scoping in `UserController::scoped()` instead (tenancy is safety-critical per §2.1) with an isolation test (`StaffManagementIsolationTest`). New staff auto-inherit the creating admin's `hospital_id`, mirroring `BelongsToHospital`'s auto-fill-on-create behavior for a model that can't use the trait itself.
- 2026-07-18 — Staff creation via `/admin/users` now always generates a random temporary password (mirroring `AdminUserSeeder`'s C14 pattern) and emails it via the existing `WelcomeCredentials` mail, instead of letting the creating admin type one in. Reason: consistency — there should be exactly one way new accounts get a password in this system, not "seeded accounts get a random temp password but admin-created ones get admin-typed ones". Editing an *existing* user's password remains admin-settable (a legitimate reset capability), but forces `password_change_required = true` on the affected account either way.
- 2026-07-18 (Phase 0 Step 6) — Confirming three scope boundaries HMS_PLAN.md already sets, per plan rule 7 ("record the decision... and continue"): **offline sync is out of scope for v1** (constraint D19 — the legacy system's `SyncQueue`/`SyncRecord`/`OfflineSyncController` were 0-byte and unreferenced; if/when built for field/rural use, conflict resolution, on-device PHI encryption, and queue-and-replay semantics get designed up front, not scaffolded speculatively). **Geofencing/`device_locations` is out of scope** (HMS_PLAN.md §4 — a legacy orphan feature with no product requirement here). **The legacy PM/projects-and-clients module is out of scope** for an HMS unless explicitly requested (§4) — nothing from it carries forward beyond what already retired to `_legacy` in Phase 0 Step 1.
- 2026-07-19 (Phase 1 Step 7) — Set explicit middleware `priority()` so `ResolveHospital` runs **before** `SubstituteBindings`. Reason: `ResolveHospital` was *appended* to the web/api groups, i.e. after `SubstituteBindings`, so implicit route-model binding of a tenant model resolved the record *before* the tenant context was set — an unscoped read that let one hospital open another's patient by UUID (caught by `PatientTenancyIsolationTest`, which returned 200 instead of 404). Fixing it once at the pipeline level makes every current and future tenant model's implicit binding tenant-safe, rather than forcing each controller to re-implement explicit scoped lookups. `ResolveHospital` only needs the session (not the full auth middleware), so running it right after CSRF/before bindings is safe.
- 2026-07-19 (Phase 1 Step 7) — Patient `bank_details` uses the `encrypted` cast and is added to `$hidden` (C12). Light insurance fields (`insurance_provider`, `insurance_member_no`) live on the patient row for now; the full insurance module (providers, claims lifecycle) is Phase 4 §7.17 — these two columns are a convenience capture, not the claims system, and will coexist with it.
- 2026-07-18 (Phase 1 Step 7) — Prepaid card money movement lives entirely in CardService: DB transaction + lockForUpdate on the card row, bcmath scale-2 (amounts kept as strings from FormRequest to column), append-only card_records ledger (UPDATED_AT=null) with a balance_after snapshot as source of truth. Reason: constraint F (no lost updates), no float drift, auditable history.
- 2026-07-18 (Phase 1 Step 7) — card_number stored encrypted + looked up by card_hash = hash_hmac('sha256', number, app.key), unique per hospital; only masked() is ever shown. Reason: C12 (sensitive at rest) while keeping uniqueness/lookup without persisting plaintext.
- 2026-07-18 (Phase 1 Step 7) — patient documents stored on the private `local` disk under patients/<hospital>/<patient>/… and streamed through a policy-gated controller, never a public URL. Reason: C12 — PHI must not be web-served directly.
- 2026-07-18 (Phase 1 Step 7) — PatientDependentRequest scopes its `exists:patients,uuid` rule to the current hospital manually, because Laravel's exists rule runs a raw query that ignores the Eloquent global scope; without it a cross-tenant uuid would validate and leak existence before the scoped fetch 404'd it.
- 2026-07-18 (Phase 1 Step 8) — departments/rooms/staff-profiles unique rules (name, code, user_id) are manually scoped to the current hospital in their FormRequests, and cross-entity `exists` rules (head_user_id, department_id, user_id) filter on hospital_id. Reason: Laravel's unique/exists rules run raw queries that ignore the Eloquent global scope, so unscoped they would both collide across tenants and leak the other tenant's rows' existence. Same class of fix as the dependents exists rule.
- 2026-07-18 (Phase 1 Step 8) — staff_profiles is a separate one-per-user table extending users, not columns on users; user_id link is immutable after creation (StaffProfileController drops it from update payload). Reason: HMS_PLAN §4 (B6 spirit) — clinical/HR data is its own concern, and login credentials never mix with specialty/licence data.
- 2026-07-18 (Phase 1 Step 8) — new migrations dated 2026_07_19_130xxx (after hospitals 2026_07_18_160000 and the Step 7 patient tables); an earlier 07_18 timestamp had them run before create_hospitals and fail the FK. Reason: migration order is filename-lexical.
- 2026-07-18 (Phase 1 Step 9) — appointment booking serializes on a lockForUpdate of the doctor's doctor_schedules rows (which must exist for any valid booking, since a booking requires a matching template window), plus a lock on the room row when set. Reason: overlap can't be expressed as a unique constraint, so a transaction + row lock on a stable pre-existing resource is the race-free way to prevent double-booking; locking the template rows is a natural, always-present serialization point (constraint F spirit).
- 2026-07-18 (Phase 1 Step 9) — appointments store both scheduled_at and a derived ends_at so overlap is a plain indexed range query (scheduled_at < end AND ends_at > start); "occupying" statuses exclude cancelled/no_show so those free the slot. Reason: simple, index-friendly, and correct without per-row duration arithmetic in SQL.
- 2026-07-18 (Phase 1 Step 9) — AppointmentStatus owns the transition table (transitionsTo/canTransitionTo); AppointmentService::transition is the only mutator and always appends an appointment_status_histories row. Reason: explicit state machine + history table per the plan's constraint; the UI derives its action buttons from transitionsTo() so it can never offer an illegal move.
- 2026-07-18 (Phase 1 Step 10a) — visit state changes and BMI go through VisitService, never Eloquent save-hooks. Reason: the legacy's fat Visit model computed billing/dosing as model side-effects on save (its top bug source, §2.3); a thin model + explicit service + history table is the rebuild. BMI computed once in recordVitals; never accepted from the client.
- 2026-07-18 (Phase 1 Step 10a) — visit_no is C-<Ymd>-<seq3>, sequence per hospital per day via a lockForUpdate count in a transaction (same pattern as PatientService), retried on the (hospital_id,visit_no) unique violation. Reason: race-free per-day numbering without a shared counter table.
- 2026-07-18 (Phase 1 Step 10a) — Step 10 split into 10a (visit core: state machine, vitals/BMI, clinical narrative) and 10b (prescriptions + DosageScheduleGenerator, medical service orders, inline patient intake). Billing rollup columns deferred to Step 11 (Billing v1) as an additive migration, so this table stays clinical-only and no money column exists before VisitBillingService owns it (avoids A4 scaffolding).
- 2026-07-18 (Phase 1 Step 10b) — DosageScheduleGenerator is a pure, deterministic service that expands a dose item into per-(date,slot) dose_item_records; a unique index (dose_item_id, scheduled_date, slot) makes regeneration idempotent. Reason: the legacy generated doses via model save-hooks (a top bug source); rebuilt as a tested service (§2.3) the plan explicitly calls out.
- 2026-07-18 (Phase 1 Step 10b) — inline new-patient intake is VisitService::intake() wrapping PatientService::register + open in one transaction, fed by a VisitIntakeRequest DTO with patientData()/visitData() splitters. Reason: the legacy stashed transient patient fields on the Visit model during "register-while-consulting" (§2.3 constraint 3 bans transient attributes on Eloquent models); a DTO + atomic service call is the safe rebuild.
- 2026-07-18 (Phase 1 Step 10b) — medical service orders + priced service catalogue deferred from Step 10 to Step 11 (Billing v1), where services are priced from the price list and invoiced. Reason: they are inherently money/billing; building them half-priced in Step 10 would split one concern across two steps. Step 10 stays clinical (visit, vitals, diagnosis, prescriptions).
- 2026-07-18 (Phase 1 Step 11a) — all money config is per-hospital and admin-editable via HospitalSettings (currency code/symbol/position/decimals/separators, tax enabled/label/rate, visit fee, invoice prefix/footer), stored on the hospital's currency column + settings.billing JSON. Nothing money-facing is hardcoded; HospitalSettings::money() formats everywhere. Reason: explicit product requirement — every hospital runs its own currency/tax; a single hardcoded currency would make the SaaS unusable outside one country.
- 2026-07-18 (Phase 1 Step 11a) — HospitalSettings is a request singleton that memoizes the hospital keyed on CurrentHospital->id(), re-resolving if the tenant context changes mid-request (super-admin hospital switch). Reason: avoid a per-call Hospital query while staying correct when the tenant changes.
- 2026-07-18 (Phase 1 Step 11a) — medical_services snapshot name + unit_price at order time; BillingService computes line_total and totals in bcmath scale-2, never a model hook. Tax from HospitalSettings applies only to non-exempt lines. Reason: invoices must reflect the price charged then, not the current catalogue price; money math stays float-free and centralized (constraint F / §2.3).
- 2026-07-18 (Phase 1 Step 11b) — Invoice is the money source of truth; amount_paid/balance are roll-ups kept in step with append-only payments rows, all written only by BillingService inside transactions (invoice locked with lockForUpdate on payment). No billing-rollup columns were added to visits (10a decision) — the invoice holds the money. Reason: single source of truth, no duplicated/for-drift totals.
- 2026-07-18 (Phase 1 Step 11b) — a card payment debits the patient's prepaid card via CardService inside recordPayment's transaction and stores card_record_id on the payment; InsufficientFundsException propagates and rolls back the whole payment (no orphan). Reason: the two money trails (invoice payments + card ledger) must reconcile and never diverge; nesting the card debit in the same transaction guarantees atomicity across both.
- 2026-07-18 (Phase 1 Step 11b) — invoice/receipt PDFs and every money display format through HospitalSettings::money(), so documents render in each hospital's own currency/tax-label/footer. Reason: the SaaS serves many currencies; hardcoding would break every non-default tenant (the dynamic-config requirement).
- 2026-07-18 (Phase 1 Step 11b) — FormRequest helper renamed method()→paymentMethod() to avoid overriding Illuminate\Http\Request::method() (returns the HTTP verb). Reason: same collision class as the earlier PatientRequest::data() fix; a child override with an incompatible return type is a fatal/PHPStan error.
- 2026-07-18 (Phase 2 Step 12a) — stock quantities/valuation move ONLY through StockService (transaction + lockForUpdate + append-only stock_movements + balance snapshot), never a model boot hook (the legacy's auto-recalc, a top bug source). Outgoing movements that would go negative throw InsufficientStockException; current_stock_value = current_quantity × cost_price, recomputed each movement in bcmath. Reason: append-only ledger is the source of truth (constraint §221), no lost updates, fully audited.
- 2026-07-18 (Phase 2 Step 12a) — delete-protection: a stock item with any movement history can't be hard-deleted (deactivate instead); a category with items can't be deleted. Reason: movement history is audit/financial evidence; the plan calls out delete-protection explicitly.
- 2026-07-18 (Phase 2 Step 12a) — low-stock/expiry alerts are a queryable board over the lowStock/expiringBefore scopes (real, unlike the legacy's empty widget); notification channels can subscribe to the same scopes later rather than duplicating the logic.
- 2026-07-18 (Phase 2 Step 12b) — DispensationService deducts stock (StockService) AND bills the drug (BillingService.addCustomLine) inside one transaction, so a dispensation's stock movements and charges are always consistent; an InsufficientStockException on any line rolls back the entire dispensation. The drug is billed as a single line (qty in the description, unit_price = line_total) so a fractional dispense bills exactly. Reason: dispensing and charging are one clinical act and must be atomic; folding qty into the description sidesteps the int-quantity limit on medical_services while keeping the money exact.
- 2026-07-18 (Phase 2 Step 13a) — a lab order snapshots each test onto its lab_order_item AND bills it on the visit (BillingService.addCustomLine) inside one transaction, mirroring dispensing; results are stored inline on the order item (1:1) rather than a separate lab_results table. Reason: order-and-charge must be atomic; a 1:1 result per ordered test is simpler and sufficient for v1 (a separate results table would add joins with no benefit at this scale). Radiology (13b) will reuse the same shape.
- 2026-07-18 (Phase 2 Step 13b) — Radiology mirrors Lab (catalogue → order-from-visit+bill → status machine → PDF) but stores a per-ORDER narrative report (findings + impression on radiology_orders) rather than per-value results, because radiology reporting is narrative not tabular. Same atomic order-and-bill pattern; RadiologyOrderStatus = ordered→scheduled→performed→reported.
- 2026-07-18 (Phase 2 Step 14) — treatment records store photos on the private local disk (streamed via a policy-gated controller, never public), and specialty charting goes in a meta JSON column rather than per-specialty tables (e.g. the legacy dental tooth-map). Reason: PHI images must not be web-served (C12); a meta JSON keeps one flexible model instead of a table per specialty.
- 2026-07-18 (Phase 3 Step 15a) — AdmissionService is the only writer of bed state; admit/transfer/discharge run in a transaction with lockForUpdate on the bed(s) so a bed can't be double-occupied. A transfer locks both beds in id order to avoid deadlock. Bed transfers are append-only events, not admission status changes. Reason: bed occupancy is a shared exclusive resource like a card/invoice — same locking discipline (constraint F).
- 2026-07-18 (Phase 3 Step 15a) — bed charge = nights × the bed's current nightly rate (min 1 night), computed on discharge in bcmath and billed to the linked visit via BillingService so IPD charges consolidate onto the patient's invoice. v1 uses the current bed's rate across the stay (not a per-bed-stay accrual); documented as a v1 simplification. Reason: keeps discharge billing simple and correct for the common single-bed stay; per-bed-stay accrual can layer on later without schema change (bed_transfers already records the timeline).
- 2026-07-18 (Phase 3 Step 15b) — nursing notes, vitals rounds and the MAR are append-only logs (UPDATED_AT = null) on an admission, accepted only while the admission is active (422 otherwise). Vitals rounds are separate from the visit's one-off triage vitals — inpatient rounds are a time series, not a single reading. Reason: clinical records are append-only evidence; an active-only guard prevents backdated entries on a closed stay.
- 2026-07-18 (Phase 4 Step 16) — Flutterwave sits behind a PaymentGateway interface (bound in AppServiceProvider) so the app never depends on a vendor SDK and providers are swappable/mockable. Money moves only in GatewayPaymentService::settle after a server-side verify() — never trusting the browser redirect's status. settle is idempotent (gateway_log row locked, marked successful once) so the callback and webhook can both call it; it rejects currency mismatch + underpayment and caps the recorded amount at the invoice balance. Reason: gateway callbacks are spoofable and fire twice (redirect + webhook); verify-first + idempotency + a signed webhook (verif-hash, constant-time) is the safe pattern.
- 2026-07-18 (Phase 4 Step 16) — added PaymentMethod::Flutterwave so a gateway payment never routes through BillingService's prepaid-card debit path (method===Card). Secrets live only in .env (C11); config/services.php reads them; .env.example has placeholders; a git-grep leak check guards each commit. The webhook route is CSRF-exempt (server-to-server) but authenticated by the verif-hash signature.
- 2026-07-18 (Phase 4 Step 17) — an insurance claim reaching Paid records a payment on its linked invoice via BillingService::recordPayment (PaymentMethod::Insurance), capped at the outstanding balance, inside the same transaction as the status change (claim.payment_id links the two). Reason: insurance settlement is real money on the invoice; routing it through the one billing ledger keeps totals consistent and reuses the overpayment guard. Added PaymentMethod::Insurance so it's never confused with cash/card/gateway.
- 2026-07-18 (Phase 4 Step 18) — closing a financial year is a posting boundary: FinancialYearService::assertPostingAllowed(date) throws ClosedPeriodException if the date is inside a closed period, and BillingService::generateInvoice calls it (resolved via app() to avoid changing the widely-used constructor). With no financial years defined, nothing is closed, so existing billing is unaffected. Per-period reporting sums payments/invoices in bcmath. Reason: accounting periods must be lockable so closed books can't be altered, while staying inert until a hospital actually defines periods.
- 2026-07-18 (Phase 4 Step 19) — notifications are queued (ShouldQueue) over database + a custom SmsChannel that wraps the existing swappable VerificationChannel (LogChannel default), so SMS has no vendor lock-in and push has a device_tokens registry. Low-stock fires only when a movement CROSSES the reorder level (was above, now at/below) to avoid alert spam; lab-result-ready notifies the ordering doctor on completion; appointment reminders run via a scheduled command (doctor in-app+SMS, patient SMS direct since patients have no login). Reason: the plan requires real notifications, not stubs; reusing the SMS abstraction and crossing-edge detection keeps them useful and quiet.
- 2026-07-18 (Phase 4 Step 20) — reports are a read-only ReportService with plain tenant-scoped aggregate queries (revenue/productivity/demographics/service-revenue/stock-valuation/occupancy); money summed in bcmath. No caching yet — acceptable at single-hospital volumes; a cache layer can wrap the service later without touching callers. Gated by reports.view (admin + accountant).
- 2026-07-18 (Phase 5 Step 21a) — the API reuses the exact domain Services + Policies as the admin panel (thin controllers just authorize, validate, and shape via JSON Resources), so RBAC and business rules can't drift between surfaces (C13). One envelope (ApiResponse) for every response incl. errors (rendered centrally in bootstrap/app.php); JsonResource::withoutWrapping() so the envelope is the sole wrapper; Sanctum-only auth (C16). ResolveHospital runs after Authenticate (middleware priority), so a token request is tenant-scoped off its user. Logout revocation is asserted at the DB (token row deleted) because Sanctum caches the resolved user within a single test process.
- 2026-07-18 (Phase 5 Step 21b–d) — API resources are added incrementally, each a thin controller over the existing Service + Policy + a JSON Resource: patients/appointments/visits get write+action endpoints; stock-items/lab-orders/invoices are read-only for now. Domain exceptions (booking conflict, illegal transition) map to 422 in the envelope via a try/catch in the controller (they're RuntimeExceptions, not ValidationExceptions, so the central handler would otherwise 500 them). @property hints added to Invoice/User/Hospital where JSON Resources access cast/relation attributes larastan couldn't infer.
- 2026-07-18 (Phase 4 Step 21) — subscription plan limits (max_staff/max_patients/max_beds in Plan.limits JSON) enforced by App\Support\PlanLimit at creation time: patients via PatientService::register (one place covering web/API/intake), staff via UserController, beds via BedController. Missing key = unlimited; no active subscription/plan = not enforced (so existing tests and super-admin are unaffected). Web catches → flash; API patient create → 403 envelope. Reason: real SaaS gating with a single reusable guard, inert until a hospital is actually on a limited plan.
- 2026-07-18 (Step 21 self-onboarding) — public self-registration creates hospital + owner + a 14-day trial subscription atomically (RegistrationService); onboarding is a stateless checklist that auto-detects completion from real data; paying for a plan reuses the SAME gateway settle() as invoices — the gateway_log carries meta.purpose='subscription' and settle() branches to SubscriptionCheckoutService::activate (convert trial → active paid period + SubscriptionPayment) instead of recording an invoice payment. Reason: one verified/idempotent settle path for all gateway money (invoices and subscriptions), no duplicated verification/webhook logic; the trial keeps signup frictionless while plan-limit enforcement (§21) gates the paid tier.
- 2026-09-13 (PJAX/Livewire Phase 0) — the custom Livewire update route registered for subdirectory hosting now carries `->middleware('web')`, and `Livewire::addPersistentMiddleware()` re-applies IsAdmin/IsSuperAdmin/EnsureSubscribed/Spatie permission+role on every Livewire request. Reason: `setUpdateRoute()` adds no middleware (Livewire's own default route does), and route-group gates otherwise run on the initial GET only — every component was re-checking access by hand, which is a convention, not a guarantee.
- 2026-09-13 (Phase 0) — EnsureSubscribed is applied to the admin, admin/api and API groups behind `tenancy.enforce_subscription` (off in tests, on everywhere else) and now selects the latest *access-granting* subscription rather than the latest row. Reason: the gate was implemented, aliased and attached to nothing, so a lapsed tenant kept full access forever; picking "the latest row" let a later cancelled record block a still-valid one.
- 2026-09-13 (Phase 0) — `super_admin` is excluded from the assignable roles of anyone who is not already a super-admin (`User::assignableRolesFor()`), and every policy's `before()` now checks the structural `isSuperAdmin()` (null hospital + role) instead of the Spatie role name. Reason: any `manage-users` holder could mint or self-assign the platform role and inherit the blanket policy bypass inside their tenant.
- 2026-09-13 (Phase 1) — the admin shell is a persisted Livewire layout: `@persist`-ed sidebar/topbar/toasts/confirm/footer, all shell JavaScript in a Vite-built `resources/js/admin.js` loaded in `<head>` (so it runs once, not on every `wire:navigate`), and `<title>{{ $title ?? yieldContent('title') }}`. Reason: body scripts are re-executed on every navigation (listener and timer leaks), and Livewire's `->title()` sets a layout *variable* while the layout was reading a Blade *section*, so every Livewire page shipped the same title and an Alpine scraper patched it after paint.
- 2026-09-13 (Phase 1) — tables render `livewire.partials.pagination` via `WithTable::paginationView()`. Reason: `WithPagination` overrides `Paginator::defaultView` with Livewire's Tailwind view at component boot, and Tailwind is not loaded in the admin, so every list shipped unstyled pagination rendered twice (mobile + desktop blocks).
- 2026-09-13 (Phase 2) — catalogue modals share `App\Livewire\Concerns\CrudModal`, and validation lives only in the FormRequest, exposed as `XRequest::rulesFor(?int $ignoreId)` for both the HTTP/API path and the Livewire component. Reason: 18 components duplicated their FormRequest's rules verbatim; the copies would drift. CrudModal also restores a soft-deleted twin instead of hitting the `(hospital_id, name)` unique index, which previously made an archived catalogue name impossible to recreate through the UI.
- 2026-09-13 (Phase 4) — document numbers come from `App\Support\Sequence` (a locked `sequences` row per hospital/key/period, seeded from existing rows). Reason: `whereYear(created_at)->lockForUpdate()->count() + 1` is not sargable (a table scan per insert) and does not prevent a concurrent insert under READ COMMITTED, so invoice/visit/patient/claim numbers collided under load and relied on a retry loop.
- 2026-09-13 (Phase 4) — appointment booking is serialised with an atomic cache lock per (hospital, doctor, date) in addition to the row locks. Reason: `SELECT … FOR UPDATE` over a range that matches no rows takes no lock under READ COMMITTED, so two concurrent bookings for the same free slot both passed the overlap check.
- 2026-09-14 (demo data) — DemoSeeder gives every demo hospital an active subscription and seeds one full clinical/billing journey per tenant through the domain services, restoring model events for that block. Reason: with the subscription gate now enforced a demo tenant without a subscription is locked out of its own data, and the seeder previously stopped at patients and stock, so most screens were empty shells; the services need the `BelongsToHospital` creating hook that `DatabaseSeeder`'s `WithoutModelEvents` mutes.
- 2026-09-16 (onboarding) — hospital setup is mandatory: "Skip for now" and the `onboarding_skipped` session flag are gone, and the required set grew to hospital details, currency/invoice numbering, a department, an ACTIVE priced service and a colleague. Reason: the gate previously suggested setup rather than requiring it, so hospitals reached the system unable to bill (no currency or price list), schedule (no department) or delegate (no staff), and produced unidentifiable invoices. Rooms, wards and catalogues stay recommended because they depend on which modules a hospital uses.
- 2026-09-16 (onboarding) — the wizard completes each step in place through the module's own FormRequest rules and services (StaffService, the Department/Service models) rather than linking away to each module. - 2026-09-19 (Offline-first, Phase 0) — Reopened the 2026-07-18 "offline sync out of scope for v1" decision at the user's request, and answered it with a design rather than scaffolding: `docs/OFFLINE_FIRST_IMPLEMENTATION_PLAN.md`. The finding that shapes everything is that the back office is 105 Livewire components, whose state, validation and rendering all live on the server — so no service worker can make them work offline, and queue-and-replay of `/livewire/update` is unsafe (an encrypted server-side snapshot replayed hours later writes against changed data with no conflict detection). The recommendation is therefore a bounded, client-rendered Field Mode covering ten append-only-or-versioned workflows, beside the Livewire panel rather than instead of it. Reason: an offline capture app is achievable and safe; an offline everything app is an SPA rewrite that `docs/frontend-spa-proposal.md` already decided against on better evidence than this request changes.
- 2026-09-19 (Offline-first, Phase 0) — No financial operation is offline-capable in phase 1. Reason: `Payment.balance_after`, `Invoice.balance` and `PatientCard.balance` are caches of append-only ledgers computed under row locks and guarded by `FinancialYear`; a device cannot compute them, and a receipt naming a balance the server disagrees with is worse than no receipt. Likewise no human-facing number (`patient_no`, `visit_no`, `invoice_no`) is ever allocated on a device — `Support\Sequence` allocates under `lockForUpdate`, and a provisional number that later changes actively misleads whoever wrote it on a specimen bottle.
- 2026-09-19 (Offline-first, implementation) — `PatientService::createWithNumber` now KEEPS a caller-supplied `uuid` instead of overwriting it with a fresh one. Reason: a patient captured on a device is minted there, and the record must arrive with the id it already has — the device has been showing it, other records captured in the same breath reference it, and a retry is only safe because the id identifies the same person both times. Reassigning it made every offline registration unmatchable and would have duplicated it on the next attempt. Validated, not trusted: a caller sending a non-uuid still gets a fresh one.
- 2026-09-19 (Offline-first, implementation) — Added `App\Observers\SyncRevisionObserver`, an Eloquent observer, despite the standing rule that business logic never lives in model save-hooks. Reason: a revision counter is infrastructure in the same family as `updated_at` — it carries no rule and changes no meaning — and it must catch every write path including the twenty-eight services and the raw ones, or a patient edited in the admin panel gets no revision and no device ever pulls it. The alternative is remembering to call it in every writer, which is the same as not having it. It hooks `saving` (before the write, one UPDATE, no recursion) and falls back to `CurrentHospital` for the hospital id because `saving` fires before `BelongsToHospital` fills the column on create.
- 2026-09-19 (Offline-first, implementation) — Conflict detection for patient demographics is a three-way merge using a `base_fields` map the device sends — the values the server last CONFIRMED for the fields being changed — rather than inference from version numbers. Reason: version inference cannot explain an edit made through the online panel, so it has to assume the worst, and one receptionist changing an address blocked every offline edit of that patient. `base_version` 0 means the device has never had any version confirmed, which happens only when it created the record itself, so it is applied rather than merged.
- 2026-09-19 (Offline-first, path handling) — Nothing in the offline client or the service worker may hardcode a path from the origin root. The worker derives its base from `self.location.pathname`; the client reads a `td-base` meta tag rendered from `config('app.url')`. Reason: this installation is served from `/true-doctor/`, and the first version hardcoded `/field`, `/api/v1` and `/field-sw.js` — every one resolved to a path that does not exist, so the worker never registered and the API was never reachable. Nothing threw and no test failed; the only symptom was the browser's own error page, which is indistinguishable from being genuinely offline. `FieldModeTest` now greps the offline sources for bare root literals.
- 2026-09-19 (Offline-first, the admin door) — The service worker's scope is the whole app, not just `/field`, and a FAILED navigation to `/admin` is answered with a generated page offering Field Mode. Reason: the panel is Livewire and cannot work offline — that is architecture, not a fault — but somebody who types its URL with no connection deserves to be told, not left with "this site can't be reached". This does not weaken the rule that admin HTML is never cached: nothing is stored, and the response is only produced once the network has already refused. `admin.js` registers the worker too, which also primes Field Mode's shell for a user who never opens it directly.
- 2026-09-19 (Offline-first, conflicts) — Resolving a conflict offers exactly two answers, "keep mine" and "keep theirs", and no merge option. Reason: a merge is what the server already attempted before it gave up and asked, so offering one would be asking a person to redo work that has already failed. "Keep mine" queues a NEW operation carrying only the contested fields, with the server's current version as `base_version` and the server's current values as `base_fields` — retrying the original operation would be contested again for exactly the same reason, because it was made against a version that no longer exists. A conflict whose record has since moved past the disputed version closes itself, so nobody adjudicates a question nobody is asking any more.
- 2026-09-19 (Offline-first, lab results) — A laboratory result is the strictest entity in the offline system: `LabResultHandler` never merges, under any circumstances. A mismatched `base_version` is refused and raised for a person; a result that already exists is refused even when the versions happen to agree, because a row predating versioning carries version 1 and a filled-in value. Reason: the plan (§10.1) is explicit that a result overwritten by a stale device is a patient-safety event — somebody is dosed on a potassium reading or sent home on a haemoglobin — and there is nothing to merge anyway, since two benches reporting different numbers for one specimen is a question somebody answers with the specimen in front of them. A result is also never CREATED from a device: the line exists because a doctor ordered the test, and only the value in it comes from the bench.
- 2026-09-19 (Offline-first, lab results) — `LabService::order()` now mints a `uuid` for each item it creates. Reason: the backfill migration gave existing rows one and nothing gave new ones any, so a bench device could not name which test it was reporting a result against. Found by the handler's own tests failing validation before they reached the handler at all.
- 2026-09-19 (Offline-first, authentication) — Field Mode authenticates with the ordinary session cookie, not a stored token: `$middleware->statefulApi()` on the server, `credentials: 'same-origin'` plus an `X-XSRF-TOKEN` header read from the cookie jar per request on the client. Reason: the `api` group had no session middleware at all, so `auth:sanctum` could only ever see a bearer token and the client sends none — a fully signed-in browser got `200` on `/admin` and `401` on every sync request beside it, which means offline mode had never synced once in any browser. Every offline test passed throughout, because they all authenticate with `Sanctum::actingAs()`, which sets the user on the guard directly and so never needs a session to exist; the tests added for this assert the middleware stack itself, and the `419`/`200` pair was confirmed with curl against the running server. Cookie over token deliberately: the session cookie is `HttpOnly` and no script on the origin can read it, where a personal access token would have to sit in IndexedDB on a shared ward machine for its full 30-day life. The CSRF token is read at request time and never from the page, because the shell is served from the service-worker cache and a token baked into the markup would be days old.
- 2026-09-19 (Offline-first, authentication) — Plan phase 9's PIN and Web Crypto token wrapping will not be built. Reason: there is no stored token to wrap. Wrapping a long-lived credential with four digits, on a machine whose storage the attacker already holds, buys very little — and it would have meant putting a credential on the device in order to have something to protect. `401` and `419` are treated as one event, "you have been signed out": both put every operation back to `pending`, raise `AUTH_EXPIRED` and show a banner saying the work is still there, because retrying against a dead session is refused identically every time and a queue that never drains with no explanation is how a clinician decides the system is broken.
- 2026-09-19 (Offline-first, schema) — `devices.pull_cursor` is `text`, not `varchar(255)`. Reason: the cursor is encrypted, and Laravel's envelope — base64 of an IV, a ciphertext and a MAC — costs about 210 characters before the payload; the real one measured 288, so `POST /sync/ack` answered 500 on every call for every device. **SQLite does not enforce VARCHAR lengths at all**, so no test failed and none would have: the test added for it asserts the column TYPE, because the type is the thing that differs between the two databases. This is the second SQLite-versus-MySQL trap in this project after the table-rebuild cascade in `App\Support\SchemaKeys`, and the general rule is worth stating — a column width is not verified by this suite, so check a new one against MySQL by hand.
- 2026-09-19 (Offline-first, clinical notes) — `VisitClinicalHandler` carries the doctor's narrative (`complaints`, `diagnosis`, `doctor_remarks`) as a three-way merge in which **every field is on the never-auto-merge list**. Reason: for demographics, merging a phone number one side changed with an address the other side changed is obviously right, because they are independent facts about a person. A diagnosis is not an independent fact — two clinicians writing different ones for one visit is a disagreement about the patient, and keeping one of them by rule, or one field from each, manufactures a clinical record neither person wrote. The merge still does the useful half: a field only the device moved is applied, and a field the server moved too is raised. The uncontested half is written even when the other half is raised, so a doctor who added remarks to a visit whose diagnosis somebody else corrected does not lose the remarks over it. A visit is never created from a device (`visit_no` comes from `Support\Sequence` and opening one bills a consultation), and one past the `ongoing` stage is refused `parent_closed` rather than amended underneath an invoice the patient has already been shown.
- 2026-09-19 (Offline-first, data minimisation) — The visits pull stream carries the clinical narrative only to an actor with `visits.diagnose`; a receptionist receives the visit and its number and nothing else. Reason: two pulls in one — minimisation says a front desk does not need diagnoses on its machine, and correctness says a doctor's device MUST have them, because without a confirmed base for those fields `base_fields` arrives empty and the handler correctly treats every field as contested. Every note written offline would have come back as a conflict. The narrative is not a nicety on that device; it is the third side of the merge.
- 2026-09-19 (Offline-first, the service worker) — The Field Mode shell and the hashed assets it names are cached **together or not at all**, and a cached shell whose assets are missing is not offered — the worker answers with its door instead. Reason: `install` cached only the HTML, and the assets were cached merely as a side effect of being fetched online, so after any `npm run build` the cached document named a bundle that was neither in the cache nor on the server. Combined with a `cacheFirst` that ended in an unguarded `await fetch()`, the rejected promise reaching `respondWith` is precisely what a browser reports as `ERR_FAILED` — so "Continue in Field Mode", on the worker's own offline door, led to the browser's error page. - 2026-09-19 (Offline-first, the service worker) — The offline door asks `shellIsUsable()`, the same question `networkFirst` will ask when its link is followed. The two answering differently is not a cosmetic inconsistency — it is the whole of what the user saw. A door that promises something must be sure of it.

- 2026-09-20 (Offline-first, validation) — `resources/js/offline/validation.js` transcribes the server's `FormRequest` rules field for field and name for name, and the offline workflows use it instead of hand-rolled checks. Reason: the device accepted a date of birth in the future, which the server refuses — so the mistake was caught hours later on sync, by which point nobody remembers typing it. The messages were also nothing like the panel's, so the same mistake read differently depending on which screen you were on. Errors are returned keyed by field, as Laravel returns them, and rendered under the control they belong to with `tb-field-error` exactly as the online forms do; a stack of red banners above a form reads as a list of unrelated complaints and leaves somebody hunting for which box is wrong. This is not a security boundary and never was — the server re-validates everything — it is so a nurse finds out at the bedside.

- 2026-09-20 (Wards) — A ward carries `default_daily_charge`, its STANDARD nightly rate, and the edit form offers an opt-in "also set every bed in this ward to that amount". The rate that is actually billed stays on the bed: a side room and a bay in the same ward are not worth the same, and `AdmissionService::discharge` reads the bed. Reason for the split: making the ward the source of truth would mean a bed could never differ from it, and the first time somebody needed a private room to cost more they would be fighting the model. The ward rate is the figure a new bed starts from and the one to apply when a whole ward is repriced. Backfilled from the commonest rate among each ward's existing beds, so a hospital opens the screen and sees its own figures rather than zero.
- 2026-09-20 (Wards, money) — Repricing a ward's beds goes through `WardService::applyNightlyChargeToBeds()`, which locks the beds, saves them one at a time so each price change lands in that bed's activity log, and returns how many were OCCUPIED. The form shows that count before the button is pressed. Reason: `AdmissionService::discharge` reads `beds.daily_charge` at discharge and multiplies it by the whole stay, so repricing an occupied bed reprices every night already spent in it, at a rate that was not in force at the time. That is sometimes exactly what an administrator means — "we put the rate up, bill everybody the new one" — and sometimes the last thing they meant, so the screen states it rather than deciding. The checkbox is form state, never persisted and never defaulted on: remembering it is how somebody reprices a ward by accident the next time they rename one. A test admits a patient, reprices the ward, discharges, and asserts the whole stay is billed at the new rate — the behaviour is pinned, not assumed.
- 2026-09-20 (Inpatient billing) — A stay is billed **a night at a time**. `AdmissionService::accrueNightlyCharges()` adds one order item per completed night to the stay's own order, priced at what the bed costs when that night is billed, and `admissions:accrue-bed-charges` runs it for every open stay at 00:05. Discharge bills whatever nights are still outstanding and no longer computes anything itself. Reason: the stay used to be a single line raised at discharge — "Bed charge — 4 night(s)" — priced at the rate in force on the day the patient left. Three things were wrong with that. The bill did not exist until the end, so a relative asking what it had cost so far got nothing. A price change was retroactive: putting the ward rate up on Friday repriced Monday's night too, which is the sharp edge the ward reprice screen had to warn about. And a stay is an order on a visit, while every other kind of order accumulates the items it actually consumed. `admissions.nights_billed` is what makes the job safe to repeat: it bills the difference between the nights completed and the nights already on the bill, so a second run in a day adds nothing and the first run after three days of downtime adds the three that were missed. `bed_charge_total` is now the SUM of what was charged rather than rate × nights — with the rate free to move between nights there is no single rate left to multiply by. The totals for a stay whose rate never changed are unchanged, and the existing tests were updated to assert the new shape while keeping every figure.
- 2026-09-20 (Inpatient billing) — A night is counted as completed once the next day has started, so the admission day itself bills nothing and a same-day stay is charged its single night at discharge via the existing `max(1, …)`. That keeps the arithmetic identical to the single-line version it replaces: a stay admitted on the 15th and discharged on the 19th is four nights either way. The catch-up command takes `--date` so a hospital that was offline can be brought up to a chosen day rather than to today, and `--dry-run` so somebody can see what it would do first. It resolves `CurrentHospital` per admission, because a scheduled command belongs to no tenant and `BelongsToHospital` fills `hospital_id` from it — left unset, a bed charge would be written onto nobody's books.
- 2026-09-20 (Inpatient) — The admit dialog asks for a VISIT, not a patient. `AdmissionRequest` makes `visit_id` required and `patient_id` nullable, and the concern reads the patient off the chosen visit. Reason: a stay is an order on a visit, exactly like a lab or an imaging order, and those are raised from a visit — the admit form was the one place that started from a patient and treated the visit as an optional afterthought ("leave blank to use their open visit"). Asking for both invited them to disagree, which `AdmissionService` then had to refuse with `VisitMismatchException`; that mismatch is now unreachable from this screen rather than merely caught by it. The service still refuses it, because the API and the offline sync handlers can still be handed both. Searching costs a nurse nothing: the visit picker matches on patient name and number as well as visit number, and labels each row "Muhindo Mubaraka · V-2026…". A patient with no visit is told to open one first, with the link beside the words — the same rule every other order follows, rather than a second hidden path that opens visits as a side effect of admitting.
